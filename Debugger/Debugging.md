# Debugging

Once you press `F5`, BitMagic behaves like any other VSCode debugger: stepping, breakpoints, hovers, disassembly, memory and jump to cursor, all covered below. Its own views, like the memory and layer viewers, are on [The Debugger](/debugger/).

## Launch configuration

A session is configured the same way as any VSCode debugger: a `type: bmasm` entry in the workspace's `.vscode/launch.json`. See [The launch config](/debugger/#the-launch-config) for its properties and how to add one. `debugArgs` takes the same flags as the [standalone emulator](/emulator#command-line), for example `["--warp"]`.

## Build errors

If a build fails, the compiler's errors appear as problems in the editor (a red marker on the offending line and an entry in the Problems panel), with the full log in the **BitMagic** output channel.

## Stepping

Continue, step over, step into and step out all work against your `.bmasm` source lines, including code generated by the template engine. Where a line generated multiple instructions, stepping walks the instructions. The exception is code built up in a string variable and output as a block: it steps into a separate generated file instead of the original lines, see [Multiline Template Code](/debugger/multiline-template-code).

## Breakpoints

- **Source breakpoints**: click the gutter next to a line.
- **Conditional**, **hit-count** and **logpoints**: see [Watches and Breakpoints](/debugger/watchesandbreakpoints).
- **Function breakpoints**: not a named procedure, but a call typed into VSCode's function breakpoint box. `vram(0x1b000)` breaks on any read or write to that VRAM address; add a second address for a range, and `"R"`, `"W"` or `"RW"` to limit the direction, for example `vram(0x1b000, 0x1b200, "W")`. `vsync()` breaks on the next frame, and `vsync(100)` on a specific frame number. `beam(320, 100)` breaks every frame when the beam reaches that point, and `line(240)` is the same as `beam(0, 240)`. Beam coordinates are in the full 800x525 scan, not the scaled display mode: the visible area is x 0-639 and y 0-479, the rest is blanking. The stop lands on the first instruction at or after that point, and up to 32 distinct beam positions can be set.
- **Instruction breakpoints**: set in the disassembly view.
- **Exception breakpoints**: three filters in the Breakpoints panel. **Code Exception** fires when an [`.exception`](/compiler/directives#debugging-directives) directive is hit (on by default), **File IO Exception** when a `LOAD` call returns an error code (on by default), and **BRK Hit** when a `BRK` instruction executes (off by default).
- **Startup breakpoints**: the `breakpoints` array in the [project file](/debugger/projectfile#properties) is a list of addresses to break on as soon as the machine starts.

## Frame Control

Run **BitMagic: Open The Frame Control View** from the command palette. It shows the screen across the full 800x525 scan, so you can see the blanking area as well as the visible 640x480 (shown brighter, with a dotted edge). A red cross marks how far the beam has drawn.

The buttons underneath step the program a frame at a time:

- **Pause**: stops at the next vsync.
- **Step**: runs to the next vsync and stops again.
- **Run**: carries on as normal.

These use a `vsync()` function breakpoint, which shows in the Breakpoints panel while you're stepping and is removed when you press Run. If you already have a `vsync()` breakpoint, that one is used and left alone. The image updates every time the debugger stops; tick **Automatically Update** to keep it streaming while the program runs.

Click the image to run until the beam reaches that point; a green cross marks the target. It works like a one-off `beam(x, y)` breakpoint that doesn't appear in the Breakpoints panel, and is forgotten when the emulator next stops for any reason. Every click runs from the same place: the first click after the program stops for any other reason saves the machine, and each click after that puts it back before running, so clicking further up the screen shows the same frame drawn to that point rather than the next one. Running, stepping or restoring a snapshot starts this again from wherever it then stops. Hold the mouse button down and move it to keep running on to wherever the mouse is, so you can scrub through the frame. The frame, beam and position under the mouse are shown under the image.

When the program is stopped part way through a frame, the dropdown next to the buttons chooses what the image shows:

- **Stop at beam**: the screen as drawn so far. Below the beam is still the previous frame.
- **Stop at beam, finish the frame**: the rest of the frame drawn down to vsync, using VERA as it is now.
- **Stop at beam, render from state**: the whole frame drawn from VERA as it is now. Changes you make to VRAM or the VERA registers while paused show straight away.

Only the display is run for these. The CPU doesn't move, nothing else is clocked and no sound is made, so carrying on afterwards is exactly as if you hadn't looked. Anything the program would change later in the frame, such as raster effects from a line interrupt, isn't drawn. While the program is running the image is always the screen as it is.

Running the same stretch over and over doesn't sound good, so clicking or dragging on the image turns on the **Mute** button, and Run turns it off again. You can also toggle it yourself. It only silences the output, the emulation and any audio recording are unaffected, and it doesn't unmute a project that has `muteAudio` set.

### Snapshots

The camera button takes a snapshot of the machine: the CPU, RAM and banked RAM, VERA (including what's on screen), the other chips and the call stack. It works while the program is running as well as when it's paused, and running carries on afterwards. Snapshots are listed under the image, newest first, with a picture of the screen, the frame, where the beam was and where the program was.

Double click a snapshot to go back to it. If the program is running it's paused first, then the debugger stops at the restored point as if it had been stepped there, so you can carry on stepping, run, or restore again. Your breakpoints aren't part of a snapshot, so whatever's set now is what's used after restoring. Snapshots can be renamed and deleted, and are only kept for the debug session.

Some things aren't included:

- **The SD card**: restoring won't undo anything written to it since the snapshot, so a program that writes to the SD card could leave it out of step with the restored machine, or corrupt it.
- **The modem**: it carries on as it was, along with any connection. You're warned when you restore with the modem running.
- **The YM2151**: its state isn't saved, so FM sound may be wrong until the program next sets it up.

## Hovering over code

Hover over a name or an operand in a `.bmasm` file to see what it is and what it works out to. This works while you're editing as well as while debugging; while a session is paused, the hover shows the machine as it is now.

While you're editing, the hover comes from the last build that worked, which BitMagic makes in the background as you type:

- **A name** shows its full path, its type (constant, label, procedure, `byte`, `ushort` and so on), whether it's private, and its value. Names are looked up from the line you're on, so `loop` inside a procedure finds that procedure's `loop`. Private names in other scopes still show, as in the debugger.
- **An operand** shows the value the build used and the addressing mode, then each name in it with its value, and the expression with the values put in.
- **A directive** such as `.const` or `.byte` shows what its expression works out to, the same way.
- **Template code** (`@(...)`) shows the line it compiled to, and that line's value.
- **A KERNAL routine** also shows its documentation.

```bmasm
.const COUNT $10
    adc #COUNT+1    ; hover: `#COUNT+1` = `$11` (17), immediate
                    ;        `COUNT` App:Main:COUNT, constant, `$10` (16)
                    ;        `$10+1`
```

Until a broken edit builds again, the hover shows the previous build, so a name you've only just added won't have one yet.

While a session is paused, the hover is the value now, and expanding it shows how it was worked out:

- **A variable** shows its current value, read as its type.
- **An indexed or indirect operand** shows the value it loads now. Expanding it shows the register, the pointer for `(ptr),y` and `(ptr,x)`, and the address it ends up at.
- **An address from `$a000` up** is read from the current RAM or ROM bank, and says which.
- **IO registers (`$9f00` to `$9fff`)** aren't read, as reading some of them changes the machine (`VERA_DATA0` moves VERA's address on). The hover shows the address and says so.

```bmasm
    lda (ptr),y     ; paused, Y = 3: $99 (153)
                    ;   pointer  $4000 at $22
                    ;   address  $4003
```

The debugger's hover uses the build being debugged, so it stays right while you edit during a session.

## Disassembly

Open the disassembly view to step through raw instructions, including ROM code. Symbols from the [`symbols`](/debugger/projectfile#symbols) files and jump tables are applied, so KERNAL calls show by name.

## Memory

The Variables pane exposes `CPU.Ram`, `VERA.VRam`, the RAM and ROM banks, and the SD card as memory blocks. VSCode's hex editor can open any of them, and memory is writable while paused. The same memory can be read as typed values in an expression, for example `CPU.Ram[0x0000].Short`; see [Watches and Breakpoints](/debugger/watchesandbreakpoints).

## Jump to cursor

"Run to cursor" and setting the next statement are supported; the CPU's `PC` is moved to the chosen line.

## Not available

VSCode's native data breakpoints (right-click a variable and choose *Break on Value Change*) aren't supported; a [`vram()` function breakpoint](#breakpoints) covers the VRAM case. Editing a value directly in the Variables pane isn't supported either; use the hex editor instead.

## Running in the official emulator

The command **Run Project In The Official Emulator** builds the project and runs it in the official X16 emulator instead of BitMagic's. This is useful for checking behaviour against the reference implementation. It needs the official emulator, which the extension can download for you (see [Settings](/settings)).
